## Miner CLI, update and platform support

- **A miner CLI that explains itself** **[redeploy]** ([#160](https://github.com/full-bars/sn/pull/160)). A bare `provider`, `--help` and `help` printed all of the docopt usage and any typo ended in a panic trace. They now print a one-screen overview, each command has its own help (`provider help wallet`), an unknown command or option gets one line and a `did you mean`, and a panic is one line at a terminal. `-vv`, `PROVIDER_DEBUG=1` or a non-terminal stderr (journald, `docker logs`) keep the full trace. `start`, `login` and `network` are aliases and every existing argument list still reaches docopt unchanged.
- **Setup, status, doctor, service and update commands** **[redeploy]** ([#160](https://github.com/full-bars/sn/pull/160)). `provider setup` walks a first run. `provider status` prints one line each for running, signed in, device, connected and updates, takes `--json` and exits 0, 3 or 4. `provider doctor` checks the state folder's mode and owner, DNS, the connection, the TLS certificate against the miner's own roots, clock skew and whether updates can install. `provider service install|uninstall|start|stop|restart|status|logs` manages a systemd user or system unit or a launchd job, with a timer that runs `provider update --auto` every 6 hours. `provider start` refuses a device that was never signed in (exit 3), and a running miner keeps `miner-status.json` in its state folder. Three refusals come from the review: `service install`, `service start` and `setup` will not start a second miner on the same state folder; `provider update` run as root refuses a binary or state folder another user can change; `service install` refuses a path or environment value with a control character that would start a line of its own in a unit file.
- **Windows** **[redeploy]** ([#160](https://github.com/full-bars/sn/pull/160)). `provider wallet set` and the payout step of `setup` failed on Windows because the wallet consent store refused there. It now has native custody, and `status` and `doctor` check the state folder's owner and ACL and print the `icacls` commands that fix it. `provider service install` works without administrator rights: it writes a Startup shortcut that runs a hidden supervisor at sign-in, restarts the miner 15 seconds after a failure (not after exit 3, which means setup is needed) and runs `provider update --auto` 15 minutes after it starts and every 6 hours. `provider update` can replace a running binary on Windows and roll back. If the URnetwork installer already mines `%USERPROFILE%\.urnetwork`, `service install` refuses and the other commands hand off to its `urnet-tools.ps1`.
- **`provider update` follows this fork and installs only the miner archive** **[redeploy]** ([#160](https://github.com/full-bars/sn/pull/160)). Upstream's default source is the newest `urnetwork/build` release, which would have replaced a fork binary with upstream's through the automatic timer and dropped every fork feature. The default source is now `full-bars/sn`, and `URNETWORK_UPDATE_URL` still overrides it. The release workflow now builds the miner for all eight platforms and publishes `urnetwork-miner-<tag>-<os>-<arch>.tar.gz`, whose lone member is the miner named `provider` (`provider.exe` on Windows). The update takes only that archive and checks the digest GitHub lists. The `urnetwork-provider-*` archives hold the relay, a different program, and are never installed over the miner, so a release that carries only relay archives reports no miner download. A node the official installer set up is unaffected: `provider update` still defers to the `urnet-tools` beside the binary.
- **`provider fleet init` and diagnostics sinks** **[redeploy]** ([#160](https://github.com/full-bars/sn/pull/160)). `provider fleet init` builds a canonical fleet manifest. Regular files and macOS terminals are admitted as diagnostic sinks, and diagnostics reach Windows consoles and pipes.
- **Chain-layer work from the sync** **[redeploy]** ([#160](https://github.com/full-bars/sn/pull/160)). The upstream commits merged across the sync (53 in the first, five more in the last) include runtime 481 to 484 admissions, release-gate and rehearsal work and competition documents. The last five (runtime 483 and 484) touch 17 upstream files, none in `miner/` or `provider/`. The fork's own adaptation commit keeps the usage text and tests valid under upstream's command-line rules.

## Miner operator surfaces

- **An action ledger** **[redeploy]** ([#207](https://github.com/full-bars/sn/pull/207)). `<state>/autopilot.jsonl` is the file the control socket's `ledger` command and `urnet-tools autopilot log` already served and nothing wrote. The miner now records the decisions it takes: OOM-cap reduce, relax, clear and frozen, the kill switch forgetting a cap, thrash restarts and refusals, and trim applications at launch and on a running pool. The file is 0600, takes an inter-process lock and rotates at 256 KiB down to 128 KiB. The provider's trim `cleared` receipt is not ported, because the miner's reloader never learns which cap caused a change, so the ledger records fewer kinds rather than guessing.
- **pprof on loopback** **[redeploy]** ([#207](https://github.com/full-bars/sn/pull/207)). `URNETWORK_PPROF=127.0.0.1:6060` starts a pprof listener, off by default, serving `/debug/pprof/` (profile, heap, goroutine, allocs, block, mutex, threadcreate, trace), for use over an SSH tunnel. The miner accepts only a literal loopback IP with a port and re-checks the socket it bound, which is stricter than the relay: `0.0.0.0` and hostnames are refused. A HotSwap candidate retries the bind (address-in-use only, 90 seconds) so profiling survives a swap.
- **Resource warnings and persisted runtime tuning** **[redeploy]** ([#207](https://github.com/full-bars/sn/pull/207)). Startup logs one `[proxy][resources] warning:` line per mismatch between the Go soft limit, the box's RAM ceiling (tightest cgroup limit, else physical RAM) and the heap the pool needs. It changes nothing. A persisted `set gomemlimit` or `set gogc` is now replayed at startup; a restart used to lose it and the memory plan's default won over the operator's explicit value.
- **Memory headroom lines** **[redeploy]** ([#207](https://github.com/full-bars/sn/pull/207)). On the pressure monitor's tick, free memory under 10% of RAM (clamped to 150 to 400 MiB) for two samples logs entry, and recovery needs four samples that clear the line by 25%. Observation only, no knob. An unreadable RAM limit takes the 400 MiB cap and logs once at startup.
- **A startup host audit** **[redeploy]** ([#205](https://github.com/full-bars/sn/pull/205)). Read-only grading of the soft file-descriptor limit, `nf_conntrack_max` against the RAM-scaled target `urnet-tools optimize` writes, and `nf_conntrack_tcp_timeout_established`. It runs once, off the provide path, and no finding can stop a launch. `URNETWORK_SKIP_AUDIT=1` skips it.
- **Incident capture** **[redeploy]** ([#205](https://github.com/full-bars/sn/pull/205)). A redacted evidence bundle is written on a recovered provider-worker panic, a fatal exit, a hotswap restart that could not hand over, an OOM-cap action at startup and a thrash escalation. It is bounded to 2 MiB, 512 KiB per file, 48 files and 2 seconds, and a capture that hits a bound leaves `incomplete.txt` naming what it skipped. Pacing is one per trigger per 30 seconds and 6 per process. Credential-shaped state is listed by name, size and mode, never copied. There is no heap profile in the bundle, because the heap writer runs a GC and every capture path is a memory-pressure path.
- **Persistent error counts** **[redeploy]** ([#205](https://github.com/full-bars/sn/pull/205)). `urnet_lifetime_errors_total` never appeared in a scrape. It is now backed by `<state>/error_counts.json` and an allow-list of diagnostic codes, flushed on the lifetime collector's throttle, at shutdown, at both hotswap exits and on the fatal exit path. Retry-in-progress, success and expected-stop codes are not counted, so the series cannot report health as failure.
- **The startup disk audit runs, and its sample is sized by time** **[redeploy]** ([#171](https://github.com/full-bars/sn/pull/171), [#216](https://github.com/full-bars/sn/pull/216), [#218](https://github.com/full-bars/sn/pull/218), [#220](https://github.com/full-bars/sn/pull/220)). The audit was ported complete but nothing called it, so the three `urnet_disk_*` series were never populated and a low-space or slow-disk host got no warning. It now starts once before the providers run, bounded in bytes and wall clock, and startup never waits on it. The write loop used to stop at 16 MiB, which an NVMe finishes in about 20 ms, so the published rate was a burst figure. A 3 second budget and a 256 MiB ceiling govern now: a microSD (10 to 30 MB/s) still writes about 20 MiB, an eMMC (about 80 MB/s) about 240 MiB, an NVMe stops at the ceiling in about 85 ms. The log line carries the sample length, for example `900.0 MB/s (256 MB written in 85 ms)`. Containers still skip the benchmark unless `URNETWORK_DISK_BENCH=1`, and a host under IO pressure still skips it. The cached result records its sampling shape and an entry written by a different sampler is a miss, so the first start after the update benchmarks again. A warning on a failed OOM-cap write no longer claims a clean-window reset that did not happen.
- **Profit, billable and contract accounting** **[redeploy]** ([#209](https://github.com/full-bars/sn/pull/209)). Every billable and settled series was a structural zero; slot counters are now fed from each slot's SDK readings on the transport-health cadence. `urnet_billable_bytes_total{direction}` counts the relay's own bytes and `urnet_contract_used_bytes_total{direction}` counts the engine's per-contract accounting, the number the platform settles on, emitted from the same read so the difference is the drift this node carries (the settled family only appears when the billable one does). `<state>/billable_rate` is written every 10 seconds so `urnet-tools idle-update` can tell a real lull from a missing metric, and a 15 second `[profit]` line carries the traffic start and stop markers. `urnet_contracts_total{result="acquired"}` counts once per platform grant, and `urnet_contracts_open`, `urnet_contract_limit_bytes`, `urnet_contract_used_bytes` and `urnet_contract_utilization` gauge the contracts open now. There is deliberately no `denied` series: a refused contract never reaches the feed and the pinned SDK exports no denial event, so any value would be a claim the process cannot back.
- **A process heartbeat and pool-health aggregates** **[redeploy]** ([#209](https://github.com/full-bars/sn/pull/209)). A `[health]` line is emitted immediately and then every `URNETWORK_HEALTH_INTERVAL` (5 minutes by default, 1 minute floor), and a `heartbeat:` block in `proxy_health.state` carries `at`, `uptime`, `interval` and `stale_after`, so a monitor can tell a wedged process from a quiet one from the file alone. `urnet_proxy_pool_up_floor` (the worst the pool got in the last hour), `urnet_proxy_pool_degraded_ticks` and `urnet_proxy_pool_scope{scope="none"|"isolated"|"pool"}` say whether a failure was per proxy or wholesale, with `[health][proxies]` and `[health] Verdict:` lines. All three are omitted when the pool is empty, because `up_floor 0` is the outage signal and a direct-only or fresh node must not publish it.
- **A baseline sampler and a systemd status line** **[redeploy]** ([#173](https://github.com/full-bars/sn/pull/173), [#172](https://github.com/full-bars/sn/pull/172)). The miner wrote operator marks into `<state>/baseline.jsonl` but never sampled the box, so an upgrade had no before and after. It now writes a `start` mark at launch and a sample every 15 minutes after a 5 minute warm-up (`URNETWORK_BASELINE_INTERVAL`, one minute floor), in the relay's wire shape so `urnet-tools baseline show|compare` read it. Unknown fields are absent, never zero. `set baseline off` stops recording without deleting the file. `systemctl status` now shows the launched, up, parked and paused counts.
- **Persistent lifetime totals** **[redeploy]** ([#175](https://github.com/full-bars/sn/pull/175), [#174](https://github.com/full-bars/sn/pull/174)). The `urnet_lifetime_*` families came from a seam nothing set, so process death erased every all-time total. `<state>/lifetime_metrics.json` now holds them with a start stamp written once, `urnet_lifetime_start_timestamp_seconds` and `urnet_lifetime_start_approximate` say how far to trust it, and the dated all-time line prints when something moved. A flush that would change nothing is skipped (an unchanged store is rewritten once a day), where the old flush did a temp file, fsync, rename and directory fsync every 45 seconds, the documented cause of SD-card wear. On a hotswap the candidate now catches up to the parent's counters, so the proxies it runs keep their history. Session and contract deltas contribute zero until their counters exist.
- **A parity check** **[no redeploy]** ([#196](https://github.com/full-bars/sn/pull/196), [#208](https://github.com/full-bars/sn/pull/208)). `go run ./scripts/parity-check` lists relay files and exported declarations with no miner counterpart, exits 0, 1 or 2, and refuses an allowlist entry without a reason. Its function and type mappings are validated.

## Miner proxy pool

- **One smart-dialer scheduler, switchable live** **[redeploy]** ([#214](https://github.com/full-bars/sn/pull/214)). The smart dialer spawned a goroutine, context and five-minute timer per proxy identity, and `set smart_dialer on` reported success and did nothing until a restart. A single dispatcher with a due-time heap replaces them (the PR measures 2000 identities going from 2000 goroutines, contexts and timers to one goroutine and one timer), and `smart_dialer` is a live key again: `on` starts the scheduler, `off` cancels and joins it and allocates nothing. Targets are egress paths, keyed by proxy address (`direct` for the direct slot), so a path shared by many identities is probed once and the verdict is stamped on every member. Probing is skipped while a path is serving clients, and limited to 2 probes in flight, one connect per second and 1200 per hour, with the first round staggered across the startup grace. The measured order is not persisted, so a restart re-measures, and one path's measured cost is not injected into another identity's strategy, which would need a connect change. The key is still off by default.
- **Proxy add, remove and rotation reach the running pool** **[redeploy]** ([#187](https://github.com/full-bars/sn/pull/187)). The miner wrote a reload trigger on every `proxy add`, `remove`, `remove-dead` and `trim` and nothing read it, so each reported a hot reload that never happened. A watcher now polls the trigger every 2 seconds, starts new identities, stops removed ones and rotates an identity whose password changed. Adding a second identity at an address another identity already owns is refused with a message, because it would silently re-identify the running slot. A failed spawn no longer aborts the reconcile, and a rotation whose replacement fails is counted as lost.
- **Alive-but-poor proxies are reaped** **[redeploy]** ([#188](https://github.com/full-bars/sn/pull/188), [#210](https://github.com/full-bars/sn/pull/210)). The miner shed only by cap and by deadness, so a proxy that kept its tunnel up and carried nothing held a slot forever. A mirror of the relay's degraded reaper now ranks by lifetime and live bytes, re-verifies before cancelling, holds a reaped identity out of the desired set for the minimum down time and then releases it. It skips timeout-family failures and stands down while the outage signal is frozen. A released identity's down-since clock now restarts on its next failure; before, a released proxy could become invisible to the reaper.
- **The audit acts on what it grades** **[redeploy]** ([#194](https://github.com/full-bars/sn/pull/194)). Client counts were always `unknown` and the park cancel map was never populated, so the CLI said it was acting and nothing acted. Rules now read the identity-keyed bandwidth counters (no entry is `unknown`, a veto, and a known 0 is idle), a park cancels the slot and holds it out of the desired set, and `proxy audit release` unparks. The direct slot is never a target.
- **Pressure shedding cancels the slots it reports** **[redeploy]** ([#192](https://github.com/full-bars/sn/pull/192)). It logged a shed and lowered the persisted target while every slot kept running, so memory stayed committed and the target ratcheted down. It now cancels through the reloader's registry and persists only what it cancelled.
- **`direct off` stops the direct slot** **[redeploy]** ([#190](https://github.com/full-bars/sn/pull/190)). `direct off` printed that direct providing was disabled while the slot kept serving, which is the wrong failure for an abuse report or a legal reason. The run now owns the direct slot: it cancels the launch when the toggle goes off and parks instead of exiting, so a direct-only node stays up to take `direct on`. Startup now obeys a persisted `off`, a real change for a direct-only node on restart. There is no `direct` control-socket key, so the path is `provider direct off`. A capture-profile run still needs a restart.
- **The URL reaper and give-up ladder freeze during a platform outage** **[redeploy]** ([#185](https://github.com/full-bars/sn/pull/185), [#186](https://github.com/full-bars/sn/pull/186)). During the 2026-10-23 outage the degraded reaper dropped 249 of 498 proxies on one canary node as under-performing while the platform was unreachable. The pinned connect exports no outage signal, so `degradedReaperFrozen` was a constant false and the give-up ladder advanced on the same failures. The miner now derives the signal from its own auth stream: a pool-wide run of at least 5 failures with no success for 5 minutes freezes the reaper and makes the ladder retry every 30 seconds instead of stepping up. Any success clears it, and the verdict is deferred, not erased. A degraded-reaper cycle where every probe failed at the API stage while a tunnel was up is also treated as an unreachable platform and demotes nobody. `PROXY_OUTAGE_FREEZE_WINDOW` and `PROXY_OUTAGE_FREEZE_MIN_FAILURES` override the window and floor, and an invalid value falls back to the default. The relay `provider` gets the ranking guard: a round whose scores tie is held off.
- **A silent platform edge no longer drains egress through proxied H3** **[redeploy]** ([#219](https://github.com/full-bars/sn/pull/219)). Under `h3 all` or a count, a proxied identity runs the H3, H3-over-dns and dns-pump carriers beside its H1. Against an edge that answers nothing, every dial runs the whole QUIC PTO ladder and every carrier of every proxy redials on its own timer for as long as the outage lasts. One node on `h3 all` spent a flat 15.5 to 16.4 Mbit/s for about 15 hours of the 2026-10-23 outage, roughly 30 times more tx than rx, while nodes where only the direct identity dials H3 spent next to nothing. The pinned `full-bars/connect` has no reconnect budget, so the miner sheds the dials instead: while the miner's own outage signal reads the platform as unreachable, no proxied identity is eligible for the fallback transports. The signal counts sign-in outcomes in one-second buckets and calls an outage when 90 seconds hold at least 12 failures and not one success, after it has been watching that long, so a start-up stampede of slow first sign-ins is not mistaken for one. It is separate from the reaper's detector on purpose: that one guards blacklisting, which is destructive, so it waits five minutes and clears on a single success anywhere, while shedding H3 is cheap and reversible and should not wait. The relaunch pass restarts the affected identities a few at a time and never one with a client, H1 keeps probing the platform, and the direct identity keeps its H3. H3 comes back only when the signal reads as recovered, which takes at least 5 successes and a majority of attempts succeeding over two minutes, held for two more, so one sign-in among hundreds of failures does not restore it. It is then given back one identity every 3 seconds, because this miner has no reconnect budget to meter a relaunch of every identity just as the platform returns.
- **`set h3` changes the transport policy** **[redeploy]** ([#193](https://github.com/full-bars/sn/pull/193), [#202](https://github.com/full-bars/sn/pull/202)). `set h3` returned OK, reported no restart needed and did nothing: the relauncher and the launch record had no production caller, and the policy `h3ModePreferences` builds was only called from tests, so turning H3 off cost a reconnect and left QUIC running. A mode change now relaunches the identities whose membership moved (the replacement gets a real address claim and census admission) and the policy goes to the SDK through `SetProviderTransportSettings` right after the device is built, read back after the write. `off` is H1 only, `direct`, a count and `all` use the default set, and `on` ties H3 with H1. The SDK swaps carriers make-before-break and exposes no completion signal, so a short window on the default policy remains, and a swap that times out leaves the slot on the default until it relaunches. This is a behaviour change: on a node where H3 currently performs worse, try it on one box before a fleet rollout. The desired-set read is also pure now, so a read can no longer detach slots without the reloader recording it.
- **Proxied QUIC goes through the proxy** **[redeploy]** ([#200](https://github.com/full-bars/sn/pull/200), [#170](https://github.com/full-bars/sn/pull/170)). On a privacy network a proxied identity's QUIC could leave from the node's own address, on two paths. The platform transport never got the SOCKS5 UDP packet-connection factory the relay installs, and the bandwidth wrap dropped the field. The alt-H3 and alt-whodis API dialers, which carry the JWT, read a different settings object and fell through to a host socket. Both now go through the proxy association, the direct slot never gets a factory, and a proxy that cannot relay H3 falls back to a TCP carrier that already goes through it. Separately, a SOCKS5 UDP association is opened and the address STUN reports over it is compared with the address the proxy reports over TCP, giving one verdict per identity (ok, no-relay, exit-mismatch, unknown). H3 requires an admitting verdict and losing one relaunches the identity on H1 only.
- **Proxy-leg evidence, contract identity and dead-relay health** **[redeploy]** ([#161](https://github.com/full-bars/sn/pull/161), [#201](https://github.com/full-bars/sn/pull/201)). A proxy can pass login and still be unable to reach the platform because the dial times out inside its own connect step. Each slot's transport logger now records that on the proxy's own streak (`urnet_proxy_leg_failures`, `proxy_leg_failures` per entry in `proxy.state`, kept apart from `auth_failures` because the two drive different remedies), and a shadow sweep flags a proxy after five failures over ten minutes, only while another path reached the platform in the last five. Nothing is shed. Contract lifecycle lines name the path they ran on, `proxy[slot] (address)` or `proxy[0] (direct)`. A proxy that authenticates and then loses its relay used to stay up and rank as healthy. The miner samples `GetProviderConnected`, holds a disconnect for a 10 second confirmation window so a transport migration is not mistaken for a drop, and then marks it `recently_offline` with `DownSince`, counting `urnet_proxy_transport_drops`. An identity that authenticates and never establishes a transport still reads as up. The scrape overlays the live registry, so the drop count no longer lags up to 60 seconds ([#208](https://github.com/full-bars/sn/pull/208)).
- **URL warmup hold, slow-auth requeue and stale self lock** **[redeploy]** ([#167](https://github.com/full-bars/sn/pull/167)). Unproven URL-sourced slots hold until the curated ramp starts or a five-minute grace passes, so the URL fetcher refreshes its list on that bound too; promoted earners and the direct slot never defer. The slow-auth requeue retries after 30 seconds; it was a give-up ramp step of over an hour. A proxy lock left by the parent's own pid after an in-place hotswap exec is cleaned, where every lock consumer used to wait up to an hour. The slow-auth sentinel cannot be raised yet because the miner's auth path has no attempt-duration measurement.
- **OOM-aware start cap** **[redeploy]** ([#177](https://github.com/full-bars/sn/pull/177)). `oom_cap` was accepted, persisted and inert. When the kernel OOM-killed the box since the previous start, the next start opens 80% of what was running at death, floored at 50, at most three reductions per 24 hours, relaxing 10% per clean window. The state is `run.marker` and `oom_cap.json`. Modes are `shadow` (the default: decide and log), `on` and `off` (forget the standing cap). The cap binds the next start's launch selection, so a live mode change takes effect when the launch selection next runs, not by shedding running proxies. It combines with the operator trim, tightest wins, with the source named so a shed is not blamed on the operator.
- **Swap-thrash watchdog, host pressure sampler and escalation** **[redeploy]** ([#168](https://github.com/full-bars/sn/pull/168), [#169](https://github.com/full-bars/sn/pull/169), [#195](https://github.com/full-bars/sn/pull/195), [#198](https://github.com/full-bars/sn/pull/198), [#210](https://github.com/full-bars/sn/pull/210)). The miner had no swap or PSI read anywhere, and nothing wrote the pressure atomics, so every pressure-driven decision (fetch stretching, probe concurrency, stale thresholds, pool shrink) behaved as if the box were idle. It now samples PSI, load and available memory, descriptors, heap and per-proxy goroutines with the relay's thresholds, and detects thrash through a four-state ladder. Escalation is a thrash cap (24 hour hold, 0.6 fraction, at most 3 per 24 hours, a re-arm ladder), a gate stack ending in a durable record and exit 75, and a liveness watchdog that restarts a wedged process, in systemd and in a container behind a state-directory durability check. OpenRC hosts refuse with `no-supervisor`. A planned thrash restart is no longer reported as a rejected sign-in, and the liveness self-exit uses a bounded stderr note, because it used to log to `events.log` in the very directory whose hang fired it. Under `provide --all-operators`, a thrash exit 75 can still be misread as a sign-in quarantine; that collision exists in the relay too.
- **Panic containment** **[redeploy]** ([#189](https://github.com/full-bars/sn/pull/189), [#197](https://github.com/full-bars/sn/pull/197)). A panic in any manager goroutine killed the whole process and dropped every slot. Fifteen manager loops now restart with a backoff from 1 second to 5 minutes, counted in `urnet_loop_up` and `urnet_loop_restarts_total`. The remaining bare goroutines are supervised (admission dispatcher, retention writer, metrics flush, control-socket accept loop, degraded reaper) or contained, and a `[panic] recovered in <name>` line says which one died. A loop that panics while holding the proxy file lock still leaks that lock.
- **Trim state is visible and reported from a complete pool** **[redeploy]** ([#163](https://github.com/full-bars/sn/pull/163), [#151](https://github.com/full-bars/sn/pull/151)). `urnet-tools proxy trim` with no argument reports the effective cap and its source (operator, OOM or thrash), the configured pool size before the cap, how many proxies the cap holds back and the live counts, and `urnet-tools status` carries a `trim` row whenever a cap applies. Trim state is recorded only from a complete decision: a failed URL-cache read used to make seven configured proxies at cap five read as 2 of 2.

## Relay provider (deprecated line)

- **URL proxies launch again when the warmup hold expires** **[redeploy]** ([#157](https://github.com/full-bars/sn/pull/157)). On a node whose registered pool contains proxies that never authenticate, the warmup ratio never reached its 90% gate, so the only exit was the 60-minute backstop: every qualified URL-sourced proxy sat deferred for an hour while the running pool drained, and the URL fetcher was parked behind the same flag. LA6 showed this as `53 deferred (warmup=53)` for a full hour and then one launch burst. The fetcher's wait is now bounded the same way as the reload gate, and the reload fires when the grace expires on its own clock.
- **Lifetime counters say when they began** **[redeploy]** ([#152](https://github.com/full-bars/sn/pull/152), [#155](https://github.com/full-bars/sn/pull/155)). The `[lifetime]` and `[pqe]` lines printed an `all-time` total with no start date. The store now persists a start stamp written once and the lines read `all-time (since 2026-10-22 13:04 PDT)`. A store written before this release keeps its totals but has no recorded start, so its start is pinned to the load time, saved at once so an idle node does not re-pin a later date on every restart, and the line says the start is approximate. The process-scoped figures, `since-start` on `[pqe]` and `lifetime_recovered` and `lifetime_lost` on `[health][proxies]`, carry their own start time. The scrape gains `urnet_lifetime_start_timestamp_seconds` and `urnet_lifetime_start_approximate` (0 exact, 1 approximate).
- **Proxies that cannot carry traffic are counted and flagged** **[redeploy]** ([#159](https://github.com/full-bars/sn/pull/159)). The relay's version of the proxy-leg evidence above: `proxy-leg:N` on the `[health][proxies]` line, `urnet_proxy_leg_failures` in the scrape, and a shadow decision (at least 5 failures in a row over 10 minutes, no platform dial succeeding through the proxy, another path reaching the platform in the last 5 minutes) that logs `[proxy][shed] shadow: would shed ...` once and counts `urnet_proxy_leg_shadow_shed_total`. The LA7 canary had six such proxies among 500. Nothing is shed.
- **The idle smart-dialer goroutine is gone** **[redeploy]** ([#204](https://github.com/full-bars/sn/pull/204)). The relay spawned a goroutine, context and timer per proxy even with smart dialing off, reported the key as live-appliable when a live apply could not start probing, and keyed its shared-gateway hold by `tag[index]`, so a reload that renumbered slots locked the reloaded slot out of probing for up to two hours. Nothing is allocated while the preference is off, `smart_dialer` is restart-required in the relay, and the hold is keyed by a hash of the JWT store key (or `direct`). The key stays off by default.
- **`urnet-tools` reports the proxy trim cap** **[redeploy]** ([#151](https://github.com/full-bars/sn/pull/151)). With no argument `urnet-tools proxy trim` reports the cap, its source, the configured pool and what the cap holds back, and `urnet-tools status` shows a `trim` row. The provider's effective cap wins over the value in the file.
- **The extender keeps its lag.dev measurement key beside its identity seed** **[redeploy]** ([#158](https://github.com/full-bars/sn/pull/158)). The extender role writes the PEM private key to `.provider.extender.measurement.key` in the state directory with mode 0600 when the file is absent. It applies only to the direct slot, the only slot that runs the extender role. Back this file up with the rest of the state directory and treat it as secret.
- **The registration custody repair hints work on any system language** **[redeploy]** ([#146](https://github.com/full-bars/sn/pull/146)). The refusal named `SYSTEM` and `Administrators`, group names icacls cannot resolve on a localized Windows. The hints now use the well-known SIDs (`*S-1-5-18`, `*S-1-5-32-544`).

## Installers

- **Installers resolve releases from this repo** **[installer]** ([#162](https://github.com/full-bars/sn/pull/162), [#180](https://github.com/full-bars/sn/pull/180)). Both installers resolved and downloaded through the mirror for `urnetwork-3.23-fix`, which does not serve these tags (a real sn tag answers 404 there), so an install could pull that repo's provider on the wrong version scheme. They now use this repo's GitHub releases and no mirror fallback. When the API is rate limited, an explicit version still works and `latest` fails with a message that says to pass one. The FreeBSD tag parse no longer depends on `python3` (it tries jq, python3, then sed), a symlinked state directory is refused, and a truncated or non-executable download is refused before it replaces a working binary.
- **The FreeBSD installer refuses a symlinked shell rc** **[installer]** ([#191](https://github.com/full-bars/sn/pull/191)). The installer, running as root, appended a PATH line to the service user's shell rc and `chown`ed it, and both follow a symlink. A symlinked rc is now refused with a warning and the install carries on. A real file is rewritten through a `mktemp` file beside it and a rename, keeping its mode. A test runs the installer block in a sandbox and requires the pre-fix version to be exploitable.
- **`urnet-tools install-service` for OpenRC and FreeBSD** **[installer]** ([#165](https://github.com/full-bars/sn/pull/165)). OpenRC and FreeBSD had control commands but nothing could write a service definition, and the FreeBSD lifecycle told operators to run a command that was never registered. `install-service` takes `--user`, `--binary` and `--dry-run`, renders an OpenRC init script or an rc.d script atomically, enables it with `rc-update` or `sysrc` and refuses a root service user. FreeBSD uninstall now disables the rc.d service as well as deleting the binary. The OpenRC restart-policy paragraph no longer describes a backoff openrc-run does not have.

## Security and correctness

- **A claim URL that carries credentials is refused** **[redeploy]** ([#164](https://github.com/full-bars/sn/pull/164)). A claim URL such as `https://api.example@evil.example` passed validation and the provider token went to the host after the `@`; a test observed two requests reaching that host before any refusal. The URL is now validated with the shared hotkeywallet rule before the client strategy is built and before any token read.
- **Directory flushes go through one helper** **[redeploy]** ([#181](https://github.com/full-bars/sn/pull/181)). The seed custody and the commitment oracle flushed directories directly, so the Windows policy (no directory flush exists there) lived in more than one place. Both use `durablesync`; there is no change on Unix.
- **The default memory plan is clamped to host RAM** **[redeploy]** ([#203](https://github.com/full-bars/sn/pull/203)). The 20 MiB per-provider floor was applied before multiplying back out, so 2000 providers on an 8 GiB host got a 117 GiB soft limit, which `ensureMemoryLimit` accepted, leaving GC with no pressure signal. The soft limit is now at most 4/5 of RAM, the device target stays at the floor, and an over-subscribed plan logs a `[mem] over-subscribed` line. `--max-memory` is unchanged.
- **The miner stops claiming what it does not do** **[redeploy]** ([#198](https://github.com/full-bars/sn/pull/198), [#199](https://github.com/full-bars/sn/pull/199)). `proxy_traffic.state` is filled from the live bandwidth registry instead of an always-empty table. Per-proxy series now match proxies with credentials. A log line that printed `2 prox2 ies` is fixed. `node_name`, `ip_version` and `h3_datagram` are accepted but have no consumer, so the control reply carries `effect=live|restart|none` and `set` prints the real effect instead of `applied live`. Metric seams with no source are marked unsupported instead of publishing zeros, and the deferred critical log is flushed every 30 seconds and at shutdown, where runtime lines used to sit unwritten.

## Library pins

- **The connect, sdk and server pins move together** **[redeploy]** ([#156](https://github.com/full-bars/sn/pull/156), [#178](https://github.com/full-bars/sn/pull/178)). connect goes from the fork's `42a8c3348` to `6eeb86ec7` (the synced `3b9bbd5bb`, which carries upstream connect up to `df0482798` plus four fork commits in the transfer layer, then the dial observer the proxy-leg evidence rides on). sdk goes from `0fefcf85f57b` to `4115b3168`: first `a9f1c1c7`, 25 commits past the old pin, then one commit that pins the deployed SN25 vault in the SDK defaults. server goes from `0fd9ce9708ea` to `05cc5e86`. They have to move together: the newer connect moves tunables into settings and removes APIs the old sdk used, the newer sdk needs the resident move code the newer connect adds, and the server module compiles against connect internals. Most of what follows ships through the pins; the sn-side code is the entries above.
- **Transfer reliability** **[redeploy]**. Zero-window flows are recovered, ACK overflow wake-ups are coalesced, receive eviction feedback wake-ups and discovery targets are fixed, continuous receiver head evidence is preserved across mixed ACK clocks, busy channels are kept through probe expiry and admission refusal, extra application pacing is disabled while delivery windows are preserved, and cached WebRTC answers are replayed for matching repeated offers.
- **Network changes and discovery** **[redeploy]**. A network change cancels a dial in flight and re-dials on the new path, a cancelled dial no longer counts toward the degraded gate, each window's resize loop wakes and its platform-error backoff starts over (a rate-limit backoff is kept), pacing is remeasured once per path generation, and discovery slows after unproductive passes and ends on a network change or a lost exit. These target devices that move between networks; a fixed-address server node will mostly not exercise them.
- **Resident moves** **[redeploy]**. The migrate message gains `move_id`, a kind (drain, advisory or compulsory), per-family target addresses, `close_time` and `prefer_duration`, so the platform can send a client to a specific edge address while it keeps the platform hostname. Auth gains `resident_move_version`, and a new result frame reports a decline or failure. A strict move dials its target direct and is refused before the dial on a relay, and a move never breaks a migration before it makes. A drain migrate still decodes as a drain and older clients ignore the new fields. The SDK moves the provider's transports at the platform's direction and declines advisory moves while an app is backgrounded or on a metered link. This release changes none of sn's own settings, so whether a given provider advertises the capability follows the SDK defaults.
- **Extenders ride on the provider row** **[redeploy]**. Each provider row carries its extenders and addresses, a stayed-on exit is pinned to the extender that carried it, and the pin is kept through a resident move.
- **Fork changes in the transfer layer** **[redeploy]**. Timeout resends spend credit earned by frames that reached the wire, so a silent peer stops consuming while a slow live peer is unaffected; credit is refunded for a resend that never went out, and recovery resends are counted at their own depth. This is shadow by default: the gate only refuses in enforce mode, so no behavior changes until enforcement is turned on. The retained-ack timeout now comes from configuration, and zero keeps the shipped behavior.
- **SDK** **[redeploy]**. Device RPC limits come from settings, native packet reads are independent of remote admission waits, hosted H1 sessions have an explicit API-alternate policy, `NetworkChanged` is exported for processes without a device, and native network space identity is exposed across the bindings. Go 1.27.3 is the floor for the SDK and connect modules, matching the toolchain this release is built with.

## Deploy notes

- **The miner and the relay provider need a redeploy.** Every **[redeploy]** entry is in the built artifact.
- **The installers and `urnet-tools` need a refresh** for the **[installer]** entries (release source, state-directory and rc hardening, `install-service`).
- **The first update to this release is manual.** The base release publishes no miner archive, so a miner on it cannot take this release through `provider update`. After this release, updates follow `full-bars/sn` by default.
- **`h3` behaviour changes on miners that set it.** `set h3` now changes the policy, so a node on `h3 off` stops QUIC and a node on `h3 all` or a count sheds proxied H3 during an outage. Miners on the default `h3 direct` dial H3 from the direct identity alone. During an outage the log shows `[h3] platform unreachable: proxied identities drop H3 ...` after about 90 seconds without a successful sign-in, and `[h3] platform answering again: proxied identities get H3 back, one every 3s` once the platform has answered for a sustained stretch.
- **`direct off` now persists across restarts** for a direct-only node, where it used to serve anyway.
- **Build with the sn version symbol:** `-X main.Version=<tag> -X main.VersionStamp=URNET_VERSION_STAMP=<tag>`, as the release workflow does.
- **New environment variables:** `URNETWORK_PPROF`, `URNETWORK_SKIP_AUDIT`, `URNETWORK_DISK_BENCH` (containers), `URNETWORK_HEALTH_INTERVAL`, `URNETWORK_BASELINE_INTERVAL`, `PROXY_OUTAGE_FREEZE_WINDOW`, `PROXY_OUTAGE_FREEZE_MIN_FAILURES`. All are optional.

## Caveats

- None of the miner entries has been confirmed on a live node. Most were verified by unit tests and, per the PR bodies, `go build`, `go vet` and the miner test suite.
- The H3 shed has not been run against a live outage. The first 90 seconds of an outage still leak on an `h3 all` miner, because the signal needs its window; a shorter window would catch it sooner at the price of reading a slow start as an outage. The thresholds (90 seconds, 12 failures, 5 successes, a 50 percent majority, a 2 minute hold, a 3 second restore pace) are reasoned from this miner's sign-in rates and the one measured outage, not tuned on more than that. The connect dependency is still ungoverned, so a change that widens H3 elsewhere could reopen this.
- `set h3` and the carrier swap leave a short window on the SDK default policy, and a swap that times out leaves a slot on the default until it relaunches.
- The `oom_cap` default is `shadow` and the transfer-layer retry budget is shadow by default; neither enforcement path is exercised in production by default.
- The thrash escalation has no OpenRC supervisor path, and several metric families (sessions, errors by class, DoH failures, `denied` contracts) are still unsupported in the miner because their sources are not exported by the pinned dependencies.
- The proxy-leg shadow flag has not been soaked, so which proxies it would flag in production is not known.
- A proxy that authenticates and never establishes a transport still reads as up.
- Three connect tests failed on the fork's own main before the pin sync and passed on upstream alone: `TestControlDialNetworkNeverNarrowsAnIPLiteral`, `TestSmartDialerOrdersTheSerialPath` and `TestSmartDialerOrdersTheParallelPath`. They are fork-side and were being diagnosed when this draft was written; whether they still fail was not re-checked.
- The blocklist and CFAA data come along with the connect pin. The data build they carry was not verified for this draft.
