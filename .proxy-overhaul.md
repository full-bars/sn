# Proxy lifecycle overhaul design

## Design

Use one owner for each reloader slot's lifecycle: a generation token is created when a slot is seeded or replaced, and only completion/cancellation for that exact generation may withdraw it or unregister its bandwidth state. Worker failures feed a bounded retry path that rechecks current eligibility instead of leaving dead entries marked running.

Use one serialized state transaction for proxy-manager state writers, including health persistence. Runtime additions must reconcile identity and provenance within APPLY under that transaction, without replaying startup-only OOM, earnings, or legacy-import side effects. Warmup is process-lifetime state, not persisted-state state. Credential verification and rotation swap are a single decision: replace only on verified credentials and otherwise leave the old value unchanged.

## Deliberately out of scope

- No push, PR, merge, deployment, or writes outside this worktree.
- No rerun of startup-only OOM/earnings/import side effects during runtime APPLY.
- No unbounded retry loop and no retry that bypasses current eligibility.
- No replacement of a credential that did not verify, and no deleting/reverting pre-existing user changes.
