## 3. Release Pipeline — urnet-tools Parity Gap

`3.23-fix` uploads:

- **Standalone binaries** (`urnet-provider-<os>-<arch>`, `urnet-tools-<os>-<arch>`, `urnet-docker-<os>-<arch>` — naming to confirm against `.goreleaser.yml`/`release.yml`)
- **Tarballs** bundling the same
- Built from repo root for all three modules

`h3-provider` uploads:

- Built from `./cmd/provider/` only
- Tarballs only — no standalone binaries per the brief
- No `urnet-tools` / `urnet-docker` artifacts

**What `urnet-tools update` expects:** the update subcommand resolves a per-platform binary name (canonical pattern is `urnet-<tool>-<os>-<arch>` — matching GoReleaser's `name_template`) from GitHub release assets, downloads it, checksums it, and atomically replaces the running executable. It does **not** untar tarballs. If the release only publishes `*.tar.gz`, `urnet-tools update` will 404 on the binary asset and fall back to (or fail on) the tarball path, breaking the upgrade flow for any already-installed `urnet-tools`.

**Actions required:**

1. Add a `release.yml` step (or restore the goreleaser config) that produces **both** bare binaries and tarballs for every platform. Tar-only releases are not parity.
2. Keep the canonical binary naming `<tool>-<os>-<arch>` consistent with the `3.23-fix` artifacts so existing installations can upgrade in place. If names change, `urnet-tools update` needs a mapping table for old→new names.
3. Verify `urnet-tools` checksums file is uploaded (usually `checksums.txt`) — the updater verifies this.
4. Since `urnet-tools/urnet-docker` porting is decided (copying `internal/urnettools`), make sure `release.yml` builds them from their new locations (`./cmd/urnet-tools/`, `./cmd/urnet-docker/`, or wherever they land) and includes their binaries in the same release output. Do not split release pipelines.

## 4. Architectural Concerns

1. **`main.go` is not "missing" — it is unported.** The comments in every `stubs_*.go` say "Will be removed when main.go is ported." Until that port lands, the `provider` package is **not** a library (it has package-init side effects: `provideStartTime`, `proxyWarmupDone`, package-level globals, `BackoffPacer` etc.) and the `cmd/provider/` main is a separate binary — but many of the ported functions *know* they belong to `main.go`. The stubs are a build pacifier, not a design. **Do not ship this state to a release branch.**

2. **Split of `main.go` into `cmd_main.go` + `cmd_*.go` is a structural change, not a migration.** If reference `main.go` had a particular ordering of init/setup (EnvSeed → control socket → provide → paceMonitor → renewal watcher), the split in `cmd_*.go` must preserve order. Verify with a startup-banner diff between reference and v2026; the banner ordering is the cheapest regression oracle you have.

3. **`stubs_batch_d.atomicBool` is a data race.** `Store` writes `a.v` with a plain assignment while another goroutine may call `Load`. It's dead code today, but if anyone wires it in, it fails `-race`. Delete now.

4. **`ApplyAutoTuning` returning `true` without applying anything is a silent lie.** Any caller that branches on the return value (`if !ApplyAutoTuning(...) { warn }`) will not warn, and runtime tuning will be silently absent. Same class of bug as `EnableProfiling` returning nil without starting a listener, and `TriggerPulse` being a no-op. In a daemon architecture, **silent no-ops on operational hooks are the highest-risk stubs.** Either implement or fail loudly.

5. **IPC / daemonization model change.** The brief states the provider is now daemonized behind a Unix socket IPC. Confirm the control-socket contract (`control_socket.go`, `sn_rpc.go`, `network_cmd.go`) matches the daemon's `cmd_*.go` subcommand surface. The reference had `main.go` own the lifecycle; now `cmd_main.go` does. Verify signals (SIGTERM/SIGUSR1 for hotswap), hotswap exec path (`hotswap_exec_path_test.go` is missing — replace it), and shutdown ordering (`control_socket_shutdown_test.go` is missing) against the daemonized path. These two missing tests are the specific ones you can least afford to lose.

6. **`read_fd_frac_*` disappearing without a stub is suspicious.** Either it's referenced by code that wasn't ported (i.e., a hidden `main.go` dependency) or it's dead in the reference (in which case delete it from the reference too, for cleanliness). It should not be in limbo.

7. **`messagePoolSummary` / `contractMetricsSnapshot.utilSum` / `ResizeMessagePoolsPerClass` all lose the same class of signal: contract/pool-level resource instrumentation that lived inside `connect`.** If the `summary` / `[health]` report is used operationally to detect a thrashing provider, these zeros will hide the problem. If not, they're dead weight. Decide *explicitly* per signal, not by stub-by-stub.

8. **Test coverage cliff.** 85 missing tests, including all `*_fix_test.go`, `*_robust_test.go`, `*_review_test.go`. The naming convention in the reference strongly implies these were written to prevent recurrence of specific production incidents. Losing them is a silent regression of *procedural* knowledge, not just code coverage. In the migration PR, either port them or add an explicit `// MIGRATION: test X intentionally deferred because Y` note — do not silently drop them.

9. **`stubs_batch_*` naming is opaque.** Before this branch is merged to `main`, consolidate stubs into real files: `atomicWriteFile` → `atomic_write.go`, `metricBytesToMiB` → `metrics_provider.go`, `applyStagedSession`+`paceMonitor` → `provide.go`, `backoffPacerWithDelay` → a `reconnect.go`, adapters into their respective `proxy_*.go`. The current layout is unmaintainable.
